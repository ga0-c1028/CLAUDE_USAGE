## 기본 정보

- **발표 형식**: 사내 전파 세미나, 30~40분 (Q&A 포함)
- **청중**: Claude를 쓰지만 Claude Code 용어(CLAUDE.md, Skill, Hook, Harness …)에는 익숙하지 않은 백엔드 개발자 약 20명
- **목표**: 어떤 앱을 만들었는지가 아니라, Claude Code로 Vibe Coding 하는 기본 개념과 사용법을 탄탄히 전달
- **원자료**: `VIBE_CODING/` 01~08 PDF (02 환경설정 제외). Harness 개념과 현재 공식 문서 기준 정정만 원자료 밖에서 가져옴
- **분량**: 23장 (본편 21장 + 데모 백업 2장)

## 전체 슬라이드 흐름

| 파트 | 슬라이드 | 시간 | 이 파트가 전달할 것 |
|---|---|---|---|
| 0. 시작 | 1–2p | 2분 | 오늘의 초점과 순서 |
| 1. Vibe Coding이란 | 3–5p | 6분 | 카파시식에서 시작해 "문서로 AI를 조종하는" 넓은 의미로. AI는 매번 새로 오는 주니어 → 환경 설계가 필요 |

- 5p "AI는 매번 새로 오는 주니어" → 6p "그래서 AI를 감싸는 환경(Harness)을 설계한다"

- 23p 내일 해 볼 3가지는 7p(CLAUDE.md), 10p(Plan mode), 12p(Skill)로 되돌아가는 요약

# Part 1. Vibe Coding이란

## 3p- 시작: 카파시식 Vibe Coding
- **핵심 메시지**: Vibe Coding의 출발은 "코드를 안 읽고 AI를 믿는 것"이었다.
- **핵심 내용**:
  - 안드레 카파시가 처음 제시한 개념
  - 자연어로 요청하면 LLM이 코드를 만들고, 사람은 결과를 보고 다시 요청
  - 코드를 세세히 읽지 않고 AI 제안을 그대로 수용, 직감으로 반복
  - 찬성: 누구나 소프트웨어를 만들 수 있다 / 반대: 책임 부재 → 보안 취약점
- **시각자료**: 기존 코딩 vs Vibe Coding 비교 표 (개발자 역할 / 코드 생성 / 필요 지식 / 개발 속도 / 디버깅) — 01장 3쪽
- **발표자 노트**: 프로토타입엔 강력하지만 운영 백엔드엔 불안하다 → 오늘 이야기의 출발점

## 4p- 넓은 의미의 Vibe Coding
- **핵심 메시지**: 오늘 말하는 Vibe Coding은 "문서와 규칙으로 AI를 조종하며 대화로 개발하는 방식" 전반이다.
- **핵심 내용**:
  - 정의: 자연어로 AI와 대화하며 코드를 만들게 하고, 사람은 방향 제시와 결과 판단을 맡는 개발 방식 전반
  - 스펙트럼: 카파시식(그냥 던지기) ←→ 문서 주도(SDD: Steering → Spec → Implement)
  - 개발자 역할의 변화: Code Writer → Problem Solver → AI Collaborator
  - 핵심 역량: 요구사항을 정확히 말하는 능력 + 결과물 품질을 판단하는 안목
- **시각자료**: 가로 스펙트럼 막대(왼쪽 카파시식, 오른쪽 SDD), "교육에서 배운 것" 마커를 오른쪽에. 아래에 역할 변화 3단계 화살표
- **발표자 노트**: 같은 "인증 기능 만들어줘"도 JWT·RS-512·해시 저장·스키마까지 명시한 프롬프트와 한 줄 프롬프트는 결과가 완전히 다르다 (01장 14쪽 예시)

## 5p- AI는 "매번 새로 오는 주니어 동료"
- **핵심 메시지**: AI는 기억을 못 하고 멋대로 창의적이다 → 그래서 AI를 감싸는 환경을 설계해야 한다.
- **핵심 내용**:
  - **새로운 동료**: 이전 대화를 기억하지 못한다 → 규칙·지침·문서화가 중요
  - **주니어**: 시킨 일은 잘하지만, 창의적으로 하면 사고가 난다 → 오버엔지니어링을 막는 지침이 필요
  - 그래서 필요한 것: AI를 감싸는 "환경"을 설계하는 일 → 다음 파트
- **시각자료**: 두 칸 카드 ("새로운" / "주니어"), 각 카드 아래 → 해결책 한 줄
- **발표자 노트**: 교육에서 가장 기억에 남은 비유. 이 두 비유가 CLAUDE.md, Skill, Hook이 왜 필요한지를 설명해 준다

# Part 2. Harness로 보는 Claude Code

## 6p- Harness란?
- **핵심 메시지**: 같은 모델이라도 결과를 가르는 건 모델을 감싼 Harness다. Claude Code가 곧 Harness다.
- **핵심 내용**:
  - Harness = Claude 모델을 감싸서 일을 할 수 있게 만드는 실행 환경
  - Claude Code가 곧 Harness
  - 구성: 모델 + 도구 실행(파일 읽기/쓰기, 셸) + 권한 + CLAUDE.md + Skill + Subagent + MCP + Hook
  - 같은 모델이라도 Harness 설정에 따라 결과가 달라진다
- **시각자료**: **Harness 다이어그램** (덱 전체의 기준 그림). 가운데 원 "Claude 모델", 바깥 링에 도구 실행 · 권한 · CLAUDE.md · Skill · Subagent · MCP · Hook. 이후 7p·10p–14p에서 같은 id로 재사용하고 해당 요소만 강조
- **발표자 노트**: claude.ai 채팅과 Claude Code의 차이는 모델이 아니라 Harness. Harness라는 말은 교육 자료에 없고, 구성 요소를 하나로 묶으려고 추가한 틀이라고 밝히기

## 7p- CLAUDE.md와 Auto memory
- **핵심 메시지**: CLAUDE.md는 내가 쓰는 규칙, Auto memory는 Claude가 쓰는 기록. 둘 다 "참고"이지 "강제"가 아니다.
- **핵심 내용**:
  - **CLAUDE.md**: 내가 직접 쓰는 규칙. 세션마다 자동으로 읽힘
    - 위치: `~/.claude/CLAUDE.md`(개인 전역) · `./CLAUDE.md`(팀 공유) · `./CLAUDE.local.md`(개인, gitignore)
    - 하위 폴더 CLAUDE.md는 그 폴더 작업 시에만 로드 → 예: `backend/CLAUDE.md`
    - 넣으면 좋은 것: 주요 명령어, 구조, 코드 스타일, 테스트 규칙, **"오버엔지니어링 금지"**, 답변 언어
    - 200줄 이내로 간결하게, 길어지면 `.claude/rules/`로 분리
  - **Auto memory**: Claude가 스스로 적는 기록
    - `~/.claude/projects/<project>/memory/MEMORY.md`, 기본 켜짐, `/memory`에서 끄고 켬
- **시각자료**: Harness 다이어그램에서 CLAUDE.md 강조 (morph). 옆에 폴더 트리 (`~/.claude/CLAUDE.md`, `./CLAUDE.md`, `./CLAUDE.local.md`, `backend/CLAUDE.md`)와 "누가 쓰나" 2열 비교(나 / Claude)
- **발표자 노트**: 반드시 막아야 하는 건 CLAUDE.md가 아니라 Hook으로 (14p 예고)
- **교육 이후 변경**: 강의에서는 우선순위를 "System Prompt > 프로젝트 CLAUDE.md > 사용자 CLAUDE.md"로 설명했지만, 현재 공식 문서 기준으로는 발견된 CLAUDE.md 파일들이 서로 덮어쓰지 않고 모두 이어 붙여져 로드된다(상위 폴더 → 작업 폴더 순서). 또 CLAUDE.md가 없으면 AGENTS.md도 읽는다.

## 8p- 데모 A: CLAUDE.md 한 줄의 차이
- **핵심 메시지**: 같은 모델, 같은 요청. 결과를 바꾼 건 CLAUDE.md 한 파일이다.
- **핵심 내용**:
  - 예제: `stepanowon/test-svc` (Express 할일 API)
  - 같은 요청: "할일에 priority 필드를 추가해줘"
  - ① CLAUDE.md 규칙 없이 → ② "오버엔지니어링 금지, 요청한 기능만 구현" 추가 후
  - 볼 것: 바뀐 파일 수, 추가된 라이브러리·추상화, `/diff`
- **시각자료**: "LIVE DEMO" 라벨, 좌우 분할(규칙 없음 / 규칙 있음) 틀, 요청 프롬프트 한 줄
- **발표자 노트**: 진행은 `presentation/demo/DEMO.md`. 결과는 매번 다를 수 있으니 "차이의 경향"을 보여 주는 데 집중

## 9p- [백업] 데모 A 녹화 · 캡처
- **핵심 메시지**: (데모 실패 시) 라이브가 안 되면 녹화 영상으로. 규칙 한 줄로 결과가 이렇게 달라졌다.
- **핵심 내용**:
  - 데모 A 녹화 영상 (`presentation/demo/demo-a.mp4`, 리허설 때 녹화)
  - 규칙 없음: `/diff` 화면 캡처
  - 규칙 있음: `/diff` 화면 캡처
- **시각자료**: 왼쪽 큰 영상 플레이어(재생 버튼으로 시작, 음소거), 오른쪽 캡처 자리 두 개 (리허설 때 교체). 숨김 슬라이드 — 8p의 "백업 캡처 ▸"로만 들어감
- **발표자 노트**: 라이브 데모가 실패했을 때만 이 장을 쓴다. 영상을 재생하고, 필요하면 오른쪽 캡처로 결과를 짚는다

## 10p- 권한 모드와 Plan mode
- **핵심 메시지**: 큰 작업은 바로 시키지 말고 Plan mode로 계획부터 다듬는다.
- **핵심 내용**:
  - Shift+Tab으로 모드 전환
  - `default`(Manual): 매번 묻는다 · `acceptEdits`: 파일 수정 자동 승인 · `plan`: 분석·계획만
  - `auto`: 분류기 모델이 대신 검토하며 진행 · `dontAsk`: 사전 허용만 실행(CI용) · `bypassPermissions`: 격리 환경 전용
  - 팁: 큰 작업은 **Plan mode로 계획 → 다듬기 → 승인 → 실행**
- **시각자료**: Harness 다이어그램에서 "권한" 강조 (morph). 모드 6개를 "사람 개입 많음 → 적음" 축에 배치한 표. 아래에 Plan mode 4단계 흐름
- **발표자 노트**: 교육에서 가장 강조한 실무 팁. 계획 다듬기 예시(인증 방법 추천 → JWT 계획 → 필드 추가 확인 → 계획 재수립)
- **교육 이후 변경**: 강의에서는 권한 모드를 default / acceptEdits / plan / bypassPermissions 4가지로 소개했지만, 현재는 auto와 dontAsk가 추가되었다. 최신 버전에서는 auto가 터미널 대화형 세션의 기본 시작 모드이고, default는 화면에서 "Manual"로 표시된다.

## 11p- Subagent
- **핵심 메시지**: 결과만 필요한 큰 일은 Subagent에게 맡겨 메인 Context를 깨끗하게 유지한다.
- **핵심 내용**:
  - 특정 작업 전담 에이전트, **자기만의 Context**에서 일한다 → 메인 Context를 아낌
  - 정의: `.claude/agents/이름.md` (frontmatter: name, description, tools, model …)
  - 호출: 자연어("test-runner subagent로…") 또는 `@` 멘션, `/agents`로 관리
  - 활용: 여러 Subagent를 병렬 실행 / 검증된 공개 Subagent 활용 (예: awesome-claude-code-subagents)
- **시각자료**: Harness 다이어그램에서 Subagent 강조 (morph). 메인 Context 박스에서 작은 Context 박스 여러 개로 갈라졌다가 "결과 요약"만 돌아오는 그림. 옆에 짧은 frontmatter 예시
- **발표자 노트**: 긴 로그 분석, 코드베이스 탐색처럼 결과만 필요한 일에 적합. 내장 Subagent(Explore, Plan)도 이미 있다
- **교육 이후 변경**: 강의에서 model 필드 값은 sonnet/opus로 소개됐지만, 현재는 haiku, fable, inherit, 전체 모델 ID도 쓸 수 있다. permissionMode, skills, memory, isolation 같은 필드도 추가되었다.

## 12p- Skill
- **핵심 메시지**: 반복되는 작업 절차는 Skill로 문서화한다. 필요할 때만 로드되어 토큰도 아낀다.
- **핵심 내용**:
  - 작업 하나를 위한 지침 묶음: `.claude/skills/이름/SKILL.md` + 필요하면 스크립트
  - 평소엔 name·description만 로드 → 필요할 때 전체 로드 → **토큰 절약**
  - 호출: Claude가 알아서 선택 / 내가 `/이름`으로 직접
  - 예: 이 발표 자료도 `seminar-deck` Skill로 만들었다
- **시각자료**: Harness 다이어그램에서 Skill 강조 (morph). "평소: 이름+설명 한 줄" → "호출 시: SKILL.md 전체" 2단계 그림. 이 발표의 `seminar-deck` SKILL.md 캡처 또는 frontmatter 예시
- **발표자 노트**: 교육의 issue-resolver 예시(이슈 번호 → 브랜치 → 분석 → 계획 → 테스트 → 구현). Codex, Cursor 등도 Skill 형식을 지원해 사실상 표준이 되어 가는 중
- **교육 이후 변경**: 강의에서는 사용자 정의 슬래시 명령어(.claude/commands)가 "deprecated"라고 했지만, 공식 문서는 "여전히 동작하는 이전 형식이고, Skill이 권장 방식"이라고 설명한다. SKILL.md frontmatter에는 paths, arguments, effort, when_to_use 등이 추가되었다.

## 13p- MCP
- **핵심 메시지**: MCP로 DB·GitHub·브라우저를 붙이면 강력하지만, 신뢰할 수 있는 서버만 붙인다.
- **핵심 내용**:
  - AI가 외부 도구·서비스를 호출하는 표준 프로토콜
  - 백엔드 개발자에게 유용한 예: PostgreSQL, GitHub, Context7(최신 라이브러리 문서), Playwright(브라우저 테스트)
  - 설치: `claude mcp add --transport http|stdio …` / 팀 공유는 `.mcp.json`
  - 주의: 가능하면 로컬 실행 + 사용량 많고 검증된 서버만 → 사내 데이터 유출·프롬프트 인젝션 위험
- **시각자료**: Harness 다이어그램에서 MCP 강조 (morph). 바깥으로 뻗는 연결선 끝에 PostgreSQL / GitHub / Context7 / Playwright 아이콘 박스. 경고 박스 하나
- **발표자 노트**: "서울에 사는 사용자 조회해줘" 같은 자연어 DB 작업 예시. 요즘은 MCP 도구를 필요할 때만 불러와 Context 부담이 적다
- **교육 이후 변경**: 강의에서는 SSE 전송 방식도 소개됐지만 현재 SSE는 deprecated이고, http(원격) 또는 stdio(로컬)를 쓴다.

## 14p- Hook
- **핵심 메시지**: CLAUDE.md는 "부탁", Hook은 "강제". 반드시 일어나야 하는 일은 Hook으로.
- **핵심 내용**:
  - Claude Code 생명주기 이벤트에 맞춰 **반드시** 실행되는 동작
  - 대표 이벤트: `PreToolUse`(실행 전, 차단 가능) · `PostToolUse`(실행 후) · `Stop`(응답 완료) · `SessionStart`
  - 활용: 작업 완료 알림, 파일 저장 후 자동 포맷, 위험한 명령 차단
  - 설정: `.claude/settings.json`의 `hooks` / `/hooks`로 확인
  - CLAUDE.md는 "부탁", Hook은 "강제"
- **시각자료**: Harness 다이어그램에서 Hook 강조 (morph). 한 턴의 타임라인(프롬프트 → PreToolUse → 도구 실행 → PostToolUse → 응답 → Stop)에 이벤트 표시. "부탁 vs 강제" 대비 한 줄
- **발표자 노트**: "rm -rf 하지 마"를 CLAUDE.md에 적는 것과 PreToolUse Hook으로 막는 것의 차이. 백엔드 개발자에게 가장 중요한 구분
- **교육 이후 변경**: 강의에서는 이벤트 9개를 소개했지만 현재는 PostToolUseFailure, SubagentStart, PermissionRequest 등 30개 이상으로 늘었고, Hook 유형도 command 외에 http, mcp_tool, prompt, agent가 있다. 또 강의의 Prettier 예시에 쓰인 `$CLAUDE_FILE_PATHS` 환경변수는 없다. 파일 경로 등은 stdin의 JSON으로 전달된다(예: `jq -r '.tool_input.file_path'`).

## 19p- Do/Don't와 검수 루프

# Part 4. 실전 작업 흐름

## 20p- 문서 → 이슈 → Skill → 테스트 → PR
- **핵심 메시지**: 문서가 곧 AI에게 주는 컨텍스트다. 문서 → 이슈 → Skill로 개발을 반복 가능한 흐름으로 만든다.
- **핵심 내용**:
  - 기획 문서를 AI와 함께: 도메인 정의서 → PRD → 아키텍처·ERD → Swagger → 실행 계획(체크박스)
  - 실행 계획 → GitHub Issue 생성 (Stage, Label, 완료 조건, 의존성)
  - 이슈 해결 Skill: 이슈 확인·브랜치·코드 분석(병렬) → 계획 → 테스트 작성 + 구현(병렬) → 테스트 → PR
  - 머지 → GitHub Actions로 테스트·배포(CI/CD)
  - 예시 앱: Team CalTalk (팀 캘린더 + 채팅), 5일 1인 개발 목표
- **시각자료**: 가로 파이프라인 (문서 → Issue → Skill → 테스트 → PR → CI/CD), 흐르는 점선 애니메이션. Skill 단계 아래에 병렬 실행 표시
- **발표자 노트**: 이 흐름으로 백엔드 API 35개를 만들었다. 각 문서를 AI가 초안 쓰고, AI가 평가하고, 사람이 검토해서 고친다

## 21p- 실전 팁
- **핵심 메시지**: AI가 헤매지 않게 하는 건 결국 규칙, 로그, 최신 문서다.
- **핵심 내용**:
  - 하위 폴더 CLAUDE.md: "오버엔지니어링 금지", "지침에 있는 기능만 정확히 구현", 사용할 기술 스택 명시
  - 로그 중심 디버깅: 개발 환경 전용 logger → 로그를 그대로 AI에게 전달
  - 구현 중 설계가 바뀌면 문서(swagger.json, ERD)를 반드시 같이 갱신
  - 자동 테스트만 믿지 말고 수동 테스트 병행 → 결과를 테스트 시나리오에 반영
  - Context 관리: 작업 단위마다 정리, 사용량이 70%를 넘으면 `/compact`, 상태는 `/context`
- **시각자료**: 5개 팁 카드 그리드 (아이콘 + 한 줄)
- **발표자 노트**: AI가 원인을 찾게 하면 토큰과 시간이 많이 든다. 로그와 기술 이해로 사람이 힌트를 줄수록 빠르다
