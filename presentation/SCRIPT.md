# Part 0. 시작 (2분)

## 1p- Vibe Coding with Claude Code

안녕하세요. 오늘은 제가 멀티캠퍼스에서 들은 「바이브코딩으로 완성하는 풀스택 서비스」 교육 내용을 30~40분 정도로 압축해서 전해 드리려고 합니다.

교육에서는 실제로 팀 캘린더 앱을 기획부터 배포까지 만들었는데요, 오늘은 그 앱이 어떻게 생겼는지보다는 **Claude Code로 개발하는 방식 자체**에 집중하겠습니다. 다들 Claude는 이미 쓰고 계시니까, 오늘 목표는 "Claude Code를 제대로 쓰려면 뭘 알아야 하나"를 탄탄히 잡는 겁니다.

## 2p- 오늘 이야기할 것

순서는 다섯 파트입니다.

먼저 Vibe Coding이 정확히 뭔지 짚고, 두 번째로 오늘의 핵심인 **Harness라는 관점으로 Claude Code를 뜯어보겠습니다.** 여기에 시간을 가장 많이 쓰고, 중간에 라이브 데모를 두 번 하겠습니다.

그다음 AI에게 일을 잘 시키는 프롬프트 방법, 교육에서 실제로 쓴 작업 흐름, 마지막으로 주의할 점과 내일 바로 해 볼 수 있는 것 세 가지로 마무리하겠습니다.

# Part 1. Vibe Coding이란 (6분)

## 3p- 시작: 카파시식 Vibe Coding

Vibe Coding이라는 말은 OpenAI 창립 멤버였던 안드레 카파시가 처음 썼습니다.

원래 의미는 이렇습니다. 자연어로 "이거 만들어줘" 하면 LLM이 코드를 만들고, 사람은 결과만 보고 "여기 고쳐줘" 하고 다시 요청합니다. 중요한 건 **코드를 세세히 읽지 않는다**는 겁니다. AI가 제안하는 걸 그대로 받아들이고, 느낌, 그러니까 vibe로 계속 반복하는 거죠.

(비교 표 가리키며) 기존 코딩과 비교하면, 개발자는 설계자·개발자·디버거에서 프롬프트 작성자·가이드·테스터로 바뀌고, 디버깅도 코드를 이해해서 고치는 게 아니라 AI에게 에러를 주고 다시 고치게 합니다.

찬성하는 쪽은 "이제 누구나 소프트웨어를 만들 수 있다"고 하고, 반대하는 쪽은 "아무도 코드에 책임을 안 지니 보안 구멍이 생긴다"고 합니다. 솔직히 프로토타입에는 엄청 강력하지만, 우리가 운영하는 백엔드에 이걸 그대로 쓰기엔 불안하죠. 오늘 이야기는 여기서 출발합니다.

## 4p- 넓은 의미의 Vibe Coding

그런데 교육에서 실제로 가르친 건 이 원래 의미보다 훨씬 넓었습니다.

오늘 말씀드리는 Vibe Coding은 **자연어로 AI와 대화하며 코드를 만들게 하고, 사람은 방향을 정하고 결과를 판단하는 개발 방식 전반**입니다.

(스펙트럼 가리키며) 한쪽 끝에 카파시식, 그냥 던지고 받는 방식이 있고, 반대쪽 끝에는 SDD, Spec Driven Development라고 해서 명세 문서를 먼저 쓰고 그 문서로 AI를 조종하는 방식이 있습니다. 교육은 거의 이 오른쪽 끝이었어요. 도메인 정의서, PRD, ERD, 실행 계획까지 문서를 다 만들고 나서 코드를 짜게 했습니다.

예를 하나 들면, "프론트엔드 앱을 위한 인증 서비스 만들어줘"라고 한 줄로 요청하는 것과, "JWT로 인증하고, 서명 알고리즘은 RS-512, 비밀번호는 일방향 해시로 저장하고, 사용자 정보는 이런 필드로 PostgreSQL에 테이블을 만들어"라고 요청하는 것은 결과가 완전히 다릅니다.

그래서 개발자 역할도 코드를 쓰는 Code Writer에서, 문제를 푸는 Problem Solver를 거쳐, AI와 협업하는 AI Collaborator로 바뀐다고 합니다. 이때 핵심 역량은 두 가지입니다. **요구사항을 정확히 말하는 능력**, 그리고 **AI가 만든 결과가 괜찮은지 판단하는 안목**입니다. 이 안목은 결국 우리가 원래 가진 개발 지식에서 나옵니다.

## 5p- AI는 "매번 새로 오는 주니어 동료"

교육에서 가장 기억에 남은 비유가 이겁니다. AI와 개발하는 건 **매번 새로 오는 주니어 개발자와 일하는 것**과 같다고요.

"새로 온다"는 건, AI가 지난 대화를 기억하지 못한다는 뜻입니다. 어제 알려 준 규칙을 오늘은 모릅니다. 그래서 매번 알려 줘야 하고, 그러려면 규칙과 지침을 문서로 남겨 둬야 합니다.

"주니어"라는 건, 시킨 일은 잘하는데 창의성을 발휘하면 사고가 난다는 뜻입니다. 필드 하나 추가해 달랬더니 검증 레이어에 상수 파일에 리팩터링까지 해 오는 경험, 다들 한 번쯤 있으실 거예요. 그래서 "오버엔지니어링 하지 마"라는 지침이 필요합니다.

이 두 가지 문제를 해결하려면 결국 **AI를 감싸는 환경을 설계**해야 합니다. 그게 다음 파트의 주제입니다.

# Part 2. Harness로 보는 Claude Code (17분)

## 6p- Harness란?

(다이어그램 가리키며) 가운데 있는 게 Claude 모델입니다. 모델 혼자서는 텍스트를 받아서 텍스트를 내놓는 것밖에 못 합니다. 파일을 읽을 수도, 명령을 실행할 수도 없죠.

이 모델을 감싸서 실제로 일을 하게 만드는 실행 환경을 **Harness**라고 부릅니다. 말 등에 채우는 마구에서 온 말인데요, 힘은 말이 내지만 그 힘을 어디로 쓸지는 마구가 정합니다.

Claude Code가 바로 이 Harness입니다. 파일을 읽고 쓰고 셸 명령을 실행하는 도구, 뭘 허락할지 정하는 권한, 그리고 오늘 설명할 CLAUDE.md, Skill, Subagent, MCP, Hook이 전부 이 바깥 링에 붙어 있습니다.

그래서 여러분이 쓰시는 claude.ai 채팅과 Claude Code는 모델이 달라서 다른 게 아니라 Harness가 달라서 다른 겁니다. **같은 모델이라도 Harness를 어떻게 설정하느냐에 따라 결과가 완전히 달라집니다.**

참고로 Harness라는 말은 교육 자료에는 없었습니다. 교육에서 배운 구성 요소들을 하나로 묶어 설명하려고 제가 추가한 틀입니다. 이제부터 이 그림에서 하나씩 불을 켜 가면서 설명하겠습니다.

## 7p- CLAUDE.md와 Auto memory

첫 번째는 CLAUDE.md입니다. 아까 "AI는 기억을 못 한다"고 했죠. 그 해결책이 이겁니다.

CLAUDE.md는 **제가 직접 쓰는 규칙 파일**이고, Claude Code가 세션을 시작할 때마다 자동으로 읽습니다. 위치는 세 군데입니다. 홈 폴더의 `~/.claude/CLAUDE.md`는 제 모든 프로젝트에 적용되는 개인 규칙, 프로젝트 루트의 `CLAUDE.md`는 git에 올려서 팀이 같이 쓰는 규칙, `CLAUDE.local.md`는 이 프로젝트에서 저만 쓰는 규칙이라 gitignore에 넣습니다.

하위 폴더에도 둘 수 있습니다. `backend/CLAUDE.md`를 두면 Claude가 backend 폴더 작업을 할 때만 그걸 읽어서, 필요 없는 규칙으로 Context를 낭비하지 않습니다.

뭘 넣으면 좋냐면, 서버 실행·빌드 명령어, 프로젝트 구조, 코드 스타일, 테스트 규칙, 그리고 교육에서 꼭 넣으라고 한 두 가지가 **"오버엔지니어링 금지"**와 **"한국어로 답변"**입니다. 언어를 안 정하면 영어로 답하는 경우가 많거든요. 길이는 200줄 이내로 간결하게, 길어지면 `.claude/rules/` 폴더에 주제별로 나눕니다.

두 번째는 Auto memory입니다. 이건 반대로 **Claude가 스스로 적는 기록**입니다. 대화하다가 제가 "이렇게 하지 마" 하고 고쳐 주면 Claude가 그걸 메모해 두고 다음 세션에 다시 읽습니다. 홈 폴더 아래 프로젝트별 memory 폴더에 저장되고, 기본으로 켜져 있고, `/memory`에서 끄고 켤 수 있습니다.

둘 다 "메모리"라고 불리긴 하지만 누가 쓰느냐가 다릅니다. CLAUDE.md는 내가, Auto memory는 Claude가 씁니다.

그리고 중요한 점 하나. 둘 다 **강제 설정이 아니라 참고 맥락**입니다. Claude가 읽고 따르려고 노력하지만 100% 보장은 아니에요. 반드시 막아야 하는 건 뒤에 나올 Hook으로 막아야 합니다.

(교육 이후 변경 배지 가리키며) 하나 정정할 게 있습니다. 교육에서는 CLAUDE.md에 우선순위가 있어서 위에 있는 게 아래 걸 덮어쓴다고 배웠는데, 지금 공식 문서를 보면 덮어쓰는 게 아니라 **찾은 파일을 전부 이어 붙여서** 읽습니다. 그리고 CLAUDE.md가 없으면 다른 AI 도구용 규칙 파일인 AGENTS.md도 읽어 줍니다.

## 8p- 데모 A: CLAUDE.md 한 줄의 차이

말로만 하면 와닿지 않으니 직접 보여 드리겠습니다.

(DEMO.md 데모 A 진행)

교육에서 쓴 예제 저장소인데요, Express로 만든 간단한 할일 API입니다. 똑같이 두 개를 복사해 뒀고, 오른쪽에만 CLAUDE.md가 있습니다. (CLAUDE.md 보여 주며) 내용은 "오버엔지니어링 금지, 요청한 기능만 구현, 새 라이브러리 추가 금지" 이 정도입니다.

양쪽에 똑같이 "할일에 priority 필드를 추가해줘"라고 요청해 보겠습니다.

(결과 나오면 `/diff`로 비교) 바뀐 파일 수, 새로 들어온 라이브러리나 추상화가 있는지 보시면 됩니다.

같은 모델, 같은 요청인데 다른 건 CLAUDE.md 한 파일입니다. 결과는 매번 조금씩 다르게 나오지만, 규칙이 있을 때 훨씬 요청한 만큼만 한다는 경향은 확실합니다.

(차이가 작게 나오면) 요즘 모델이 좋아져서 차이가 줄었는데요, 그래도 팀 규칙을 확실히 전달하는 곳은 여기라는 걸 기억해 주세요. 리허설 때 찍어 둔 화면으로 보여 드리겠습니다. (9p로)

## 9p- [백업] 데모 A 녹화 · 캡처

(라이브 데모가 실패했을 때만 사용. 왼쪽 영상의 재생 버튼을 누른다)

지금 라이브가 잘 안 돼서, 리허설 때 녹화해 둔 영상으로 보여 드리겠습니다. 방금 하려던 것과 똑같이, 같은 요청을 CLAUDE.md가 없는 쪽과 있는 쪽에 보낸 장면입니다.

(영상이 끝나면 오른쪽 캡처 가리키며) 결과를 정리하면 이렇습니다. 왼쪽이 규칙 없이 요청한 결과, 오른쪽이 CLAUDE.md를 넣고 요청한 결과입니다. 바뀐 파일 수와 추가된 코드 양을 비교해 보시면 차이가 보이실 겁니다.

## 10p- 권한 모드와 Plan mode

다음은 권한입니다. Claude Code가 파일을 고치거나 명령을 실행하기 전에 저한테 물어볼지 말지를 정하는 게 권한 모드이고, Shift+Tab으로 바꿉니다.

(표 가리키며) 가장 조심스러운 `default`, 화면에는 Manual이라고 나오는데 매번 물어봅니다. `acceptEdits`는 파일 수정은 알아서 하고, `plan`은 분석하고 계획만 세웁니다. 교육 이후에 새로 생긴 게 `auto`인데요, 저 대신 별도의 분류기 모델이 "이 명령 위험한가"를 검토하면서 진행합니다. `dontAsk`는 미리 허용한 것만 실행하는 CI용이고, `bypassPermissions`는 모든 확인을 건너뛰기 때문에 격리된 컨테이너나 VM에서만 써야 합니다.

교육에서 가장 강조한 실무 팁이 바로 **Plan mode**입니다. 큰 작업을 바로 시키지 말고 계획부터 받으라는 거예요.

예를 들면 이렇게 합니다. 먼저 "인증 기능을 추가하고 싶은데 방법 몇 가지 추천해 줘." 그다음 "JWT 방식으로 하려면 무슨 작업을 해야 할지 계획 세워 줘." 계획을 보고 "사용자 모델에 더 필요한 필드 있는지 확인해 줘." 그리고 "그거까지 반영해서 계획 다시 세워 줘." 이렇게 계획을 여러 번 다듬은 다음에 실행을 승인합니다. 코드를 다 짜고 나서 방향을 바꾸는 것보다 훨씬 싸게 먹힙니다.

(교육 이후 변경 배지) 교육에서는 모드를 네 가지로 배웠는데 지금은 auto와 dontAsk가 추가돼서 여섯 가지이고, 최신 버전에서는 auto로 시작하는 게 기본입니다.

## 11p- Subagent

다음은 Subagent입니다. 특정 작업만 전담하는 에이전트인데, 핵심은 **자기만의 Context에서 일한다**는 겁니다.

Context가 뭐냐면, 모델이 한 번에 볼 수 있는 대화·파일·지침의 총량입니다. 이게 차면 앞의 내용을 요약하거나 잊어버립니다. 그런데 예를 들어 로그 수천 줄을 분석하거나 코드베이스 전체를 뒤지는 일을 메인 대화에서 하면 Context가 금방 차 버리죠.

(그림 가리키며) Subagent에게 맡기면, Subagent가 자기 Context에서 그 일을 다 하고 **결과 요약만** 메인 대화로 돌려줍니다. 메인 대화는 깨끗하게 유지되죠. 서로 독립적이라 여러 개를 동시에 병렬로 돌릴 수도 있습니다.

만드는 법은 `.claude/agents/` 폴더에 md 파일 하나를 두면 됩니다. 이름, 언제 쓸지 설명, 쓸 수 있는 도구, 쓸 모델을 적고, 그 아래에 역할을 적습니다. 부를 때는 "test-runner subagent로 테스트 고쳐 줘"처럼 자연어로 하거나 `@`로 멘션하고, `/agents`로 관리합니다.

교육에서는 직접 만들기보다 GitHub에서 스타 많은, 검증된 Subagent 모음을 가져다 쓰라고 권했습니다. 그리고 Explore, Plan 같은 Subagent는 이미 내장돼 있어서, 코드베이스를 탐색할 때 Claude가 알아서 씁니다.

(교육 이후 변경 배지) 교육에서는 모델을 sonnet이나 opus 중에 고른다고 배웠는데, 지금은 haiku나 메인 대화 모델을 따라가는 inherit도 쓸 수 있고, 권한 모드나 Skill, 메모리를 Subagent별로 따로 줄 수 있는 필드도 생겼습니다.

## 12p- Skill

다음은 Skill입니다. 한마디로 **반복되는 작업 절차를 문서로 만들어 둔 것**입니다.

`.claude/skills/이름/SKILL.md` 파일에 "이 작업은 이런 순서로, 이런 규칙으로 해라"를 적어 두고, 필요하면 스크립트도 같이 둡니다.

Skill의 좋은 점은 로드 방식에 있습니다. (그림 가리키며) 평소에는 Skill의 이름과 한 줄 설명만 Context에 올라가 있다가, 실제로 그 작업이 필요할 때 전체 내용이 로드됩니다. 그래서 Skill을 수십 개 설치해도 Context 부담이 적습니다. 부르는 건 두 가지 방법이 있는데, Claude가 대화 내용을 보고 알아서 고르거나, 제가 `/이름`으로 직접 부릅니다.

교육에서는 GitHub 이슈 번호를 주면 이슈 확인, 브랜치 생성, 코드 분석, 계획, 테스트, 구현까지 한 번에 하는 issue-resolver라는 걸 만들어서 백엔드와 프론트엔드를 개발했습니다.

그리고 사실 이 발표 자료도 Skill로 만들었습니다. 용어집을 지키고, 대본과 설계서를 읽고, 교육 이후 바뀐 건 배지를 달라는 규칙을 Skill에 적어 두니까, 다음에 고칠 때도 같은 방식으로 고칠 수 있습니다.

Skill은 Claude Code뿐 아니라 Codex, Cursor 같은 다른 도구도 지원해서 사실상 표준처럼 자리 잡고 있습니다.

(교육 이후 변경 배지) 교육에서는 예전 방식인 사용자 정의 슬래시 명령어가 deprecated라고 했는데, 공식 문서는 "아직 동작하는 이전 형식이고 Skill을 권장한다" 정도로 설명합니다. 지금 쓰시는 커맨드를 급하게 옮길 필요는 없습니다.

## 13p- MCP

다음은 MCP입니다. AI가 외부 도구나 서비스를 호출할 수 있게 해 주는 표준 규격입니다. USB 포트처럼, 규격만 맞으면 뭐든 꽂을 수 있다고 생각하시면 됩니다.

백엔드 개발자에게 유용한 예를 들면, PostgreSQL MCP를 붙이면 "지역이 서울인 사용자 조회해 줘"처럼 자연어로 DB 작업을 할 수 있고, GitHub MCP로 이슈나 PR을 다루고, Context7은 라이브러리의 최신 문서를 참조하게 해서 옛날 버전 코드를 짜는 걸 막아 줍니다. Playwright는 브라우저를 직접 띄워 테스트하게 해 줍니다.

설치는 `claude mcp add` 명령으로 하고, 팀과 공유하려면 프로젝트 루트의 `.mcp.json`에 넣습니다.

주의할 점이 있습니다. 편한 만큼 위험합니다. 외부 중개 서버를 쓰면 사내 데이터가 밖으로 나갈 수 있고, 외부 내용을 가져오는 서버는 프롬프트 인젝션 공격에 노출될 수 있습니다. 그래서 **가능하면 로컬에서 실행하는 서버, 사용량 많고 검증된 서버만** 쓰라는 게 교육의 권고였습니다.

예전에는 MCP를 많이 붙이면 도구 설명이 다 Context에 올라가서 부담이 컸는데, 요즘은 필요할 때만 불러와서 그 문제는 많이 줄었습니다.

(교육 이후 변경 배지) 교육에서 소개한 SSE라는 연결 방식은 이제 deprecated라서, 원격은 http, 로컬은 stdio를 쓰시면 됩니다.

## 14p- Hook

다음은 Hook입니다. 백엔드 개발자분들께 제일 중요하다고 생각하는 부분입니다.

Hook은 Claude Code가 일하는 과정의 특정 시점에 **반드시** 실행되는 동작입니다. (타임라인 가리키며) 도구를 실행하기 직전인 PreToolUse, 실행한 직후인 PostToolUse, 응답이 끝났을 때인 Stop, 세션이 시작될 때인 SessionStart 같은 시점이 있습니다.

아까 CLAUDE.md는 참고 맥락이라 100% 보장이 아니라고 했죠. 예를 들어 CLAUDE.md에 "rm -rf 절대 쓰지 마"라고 적는 건 **부탁**입니다. Claude가 대부분 지키지만 보장은 없어요. 반면 PreToolUse Hook에서 rm -rf가 포함된 명령을 막으면 그건 **강제**입니다. Claude가 뭘 판단하든 그 명령은 실행되지 않습니다.

활용 예로는 작업이 끝나면 알림 받기, 파일을 저장할 때마다 prettier나 lint 자동 실행, 위험한 명령 차단 같은 게 있습니다. 설정은 `.claude/settings.json`의 hooks 항목에 적고, `/hooks`로 등록된 걸 확인할 수 있습니다.

(교육 이후 변경 배지) 교육에서는 이벤트 아홉 개를 배웠는데 지금은 서른 개가 넘고, 셸 명령 말고도 HTTP 호출이나 LLM 판단을 Hook으로 쓸 수도 있습니다. 그리고 교육 자료의 prettier 예시에 나온 `CLAUDE_FILE_PATHS`라는 환경변수는 지금은 없습니다. 파일 경로 같은 정보는 JSON으로 들어오니까, 자료 보고 따라 하실 때 주의하세요.

## 15p- 데모 C: 작업이 끝나면 말해 주는 Hook

Hook도 직접 보여 드리겠습니다. 제일 간단하면서 체감이 큰 예시입니다.

(DEMO.md 데모 C 진행)

(settings.json 보여 주며) 설정은 이게 전부입니다. Stop 이벤트, 그러니까 Claude가 응답을 마칠 때 맥의 `say` 명령으로 "작업이 완료되었습니다"라고 말하게 했습니다.

(`/hooks`로 등록 확인 후 아무 요청) 이제 아무거나 시켜 보겠습니다.

(음성 나오면) 긴 작업을 시켜 놓고 다른 일을 하다가 소리로 끝난 걸 알 수 있습니다. 같은 방식으로 Slack에 알림을 보내거나, 파일 저장 후 lint를 돌리거나, 위험한 명령을 막을 수 있습니다.

## 16p- [백업] 데모 C 녹화 · 캡처

(라이브 데모가 실패했을 때만 사용. 왼쪽 영상의 재생 버튼을 누른다. 소리가 나야 한다)

리허설 때 녹화해 둔 영상으로 보여 드리겠습니다. 응답이 끝나는 순간 음성이 나오는지 들어 보세요.

(영상이 끝나면 오른쪽 캡처 가리키며) 설정은 이 한 블록이고, 이 settings.json 블록을 넣으면, `/hooks` 화면에 이렇게 Stop Hook이 등록된 게 보입니다. 이 상태에서 요청을 하면 응답이 끝날 때 음성이 나옵니다.

## 17p- 한눈에 보기: 무엇을 언제 쓰나

오늘 한 장만 가져가신다면 이 장입니다.

항상 알아야 하는 규칙은 **CLAUDE.md**에. 가끔 하는 정해진 작업 절차는 **Skill**로. Context를 분리해야 하는 큰 작업이나 병렬 작업은 **Subagent**에게. 외부 시스템 연결은 **MCP**로. 무슨 일이 있어도 반드시 일어나야 하는 일은 **Hook**으로.

마지막으로 **Plugin**은 이것들을 한 묶음으로 포장한 겁니다. 팀에서 자주 쓰는 Skill, Hook, MCP 설정을 Plugin 하나로 묶으면, 팀원들이 명령 한 번으로 똑같은 환경을 설치할 수 있습니다.

# Part 3. AI에게 잘 시키는 법 (5분)

## 18p- 좋은 프롬프트의 구성 요소

Harness를 잘 갖춰도 결국 AI에게 말을 거는 건 프롬프트입니다. 교육에서는 좋은 프롬프트의 구성 요소를 일곱 가지로 정리했습니다.

무엇을 할지인 Task, 배경과 제약인 Context, 어떤 형식으로 받을지인 Output Format, 해야 할 것과 하지 말 것인 Instructions, 품질 기준인 Rubric, 어떤 전문가처럼 답할지인 Role, 그리고 예시인 Examples입니다. 매번 다 쓸 필요는 없고, 중요한 작업일수록 많이 채우면 됩니다.

여기서 제일 와닿았던 게 **최소 충분 컨텍스트**라는 원칙입니다. (Before/After 가리키며) 왼쪽은 "우리 회사는 2010년에 설립되어 직원 200명이고, 개발팀은 50명이고…"로 시작해서 한참 뒤에 "사용자 목록 API 최적화해 줘"가 나옵니다. 오른쪽은 "GET /api/users, 응답 7초, 목표 2초 이하, 테이블 100만 건, 현재 쿼리는 SELECT * ORDER BY created_at, 페이지네이션 필수" 이렇게 필요한 것만 있습니다. 당연히 오른쪽이 훨씬 좋은 답을 받습니다. 정보가 많다고 좋은 게 아니라, 필요한 정보가 정확해야 합니다.

그리고 지시와 데이터는 구분자로 나눠 주세요. 교육에서는 마크다운 헤더로 섹션을 나누는 걸 권장했습니다.

## 19p- Do/Don't와 검수 루프

두 가지 더 있습니다.

하나는 **Do와 Don't를 나눠 적기**입니다. 해야 할 것만 적는 것보다, 하지 말아야 할 걸 같이 적으면 결과가 훨씬 안전해집니다. 백엔드라면 "비밀번호나 API 키 하드코딩 금지, 사용자 입력을 SQL에 직접 넣지 말 것, CORS를 별표로 열지 말 것" 같은 것들이죠. 이런 건 한 번 정리해서 CLAUDE.md에 넣어 두면 좋습니다.

다른 하나는 **검수 루프**입니다. 한 번에 완벽한 결과를 기대하지 말고, 생성시키고, 체크리스트로 평가하고, 문제점을 알려 주고, 다시 생성시키는 걸 반복합니다. 이때 멈출 기준도 정해 둬야 합니다. 품질 기준을 달성했거나, 더 돌려도 나아지는 게 거의 없거나, 큰 이슈가 없으면 멈춥니다. 안 그러면 토큰만 계속 씁니다.

반대로 피해야 할 것도 있습니다. 앱 전체를 한 번에 만들어 달라는 거대한 요청, AI 결과를 검증 없이 바로 쓰는 것, 테스트와 문서화를 생략하는 것입니다.

되돌릴 수 있어야 과감하게 시도할 수 있으니까, `/rewind`로 이전 시점으로 돌아가는 체크포인트와 git 커밋을 꼭 같이 쓰세요.

# Part 4. 실전 작업 흐름 (5분)

## 20p- 문서 → 이슈 → Skill → 테스트 → PR

이제 이걸 실제 개발에 어떻게 엮었는지 보여 드리겠습니다. 교육에서는 Team CalTalk라는, 팀 캘린더에 채팅을 붙인 앱을 5일 안에 혼자 만든다는 목표로 진행했습니다.

(파이프라인 가리키며) 먼저 문서부터 만듭니다. 도메인 정의서, PRD, 아키텍처와 ERD, API 명세인 Swagger, 그리고 체크박스로 된 실행 계획까지요. 재밌는 건 이 문서들을 전부 AI가 초안을 쓰고, AI가 평가하고, 사람이 검토해서 고친다는 겁니다. 그리고 **이 문서들이 곧 AI에게 주는 컨텍스트**가 됩니다.

실행 계획이 나오면 그걸 GitHub Issue로 만듭니다. 이슈마다 단계, 라벨, 완료 조건, 의존성을 적게 합니다.

그다음 아까 말씀드린 이슈 해결 Skill을 씁니다. 이슈 번호를 주면 이슈 확인, 브랜치 생성, 기존 코드 분석을 병렬로 하고, 계획을 세우고, 테스트 작성과 구현을 또 병렬로 하고, 테스트를 돌리고 PR을 만듭니다. PR이 머지되면 GitHub Actions가 테스트하고 배포합니다.

이렇게 해서 교육에서는 백엔드 API 35개를 만들었습니다. 핵심은 매번 즉흥적으로 시키는 게 아니라, **같은 흐름을 반복할 수 있게 만든다**는 겁니다.

## 21p- 실전 팁

교육에서 실제로 부딪히며 배운 팁 다섯 가지입니다.

첫째, 하위 폴더 CLAUDE.md에 "오버엔지니어링 금지"와 "지침에 있는 기능만 정확히 구현"을 넣고, 쓸 기술 스택도 적어 두세요. 안 그러면 AI가 axios를 쓸지 fetch를 쓸지 그때그때 다르게 고릅니다.

둘째, 디버깅은 로그 중심으로 하세요. AI에게 원인을 처음부터 찾게 하면 토큰과 시간이 엄청 듭니다. 개발 환경에서만 동작하는 logger를 만들어 두고, 에러 메시지만이 아니라 로그를 그대로 AI에게 주면 훨씬 빨리 고칩니다. 그리고 우리가 기술을 이해하고 "여기가 의심스럽다"는 힌트를 주면 더 빨라집니다.

셋째, 구현하다가 API나 스키마가 바뀌면 swagger.json과 ERD 같은 문서도 반드시 같이 고치세요. 문서가 AI의 컨텍스트니까, 문서가 틀리면 다음 작업이 틀립니다.

넷째, AI가 만든 자동 테스트만 믿지 마세요. 테스트 자체가 틀릴 수 있습니다. 수동 테스트를 같이 하고, 거기서 발견한 걸 다시 테스트 시나리오에 넣습니다.

다섯째, Context 관리입니다. 작업 단위가 끝날 때마다 정리하고, 사용량이 70%를 넘으면 `/compact`로 압축하세요. 지금 얼마나 찼는지는 `/context`로 볼 수 있습니다.

# Part 5. 주의점과 내일 해 볼 것 (3분 + Q&A)

## 22p- 어디까지 맡길까

그럼 어디까지 맡겨도 될까요.

프로토타입, 개인용 도구, 반복 작업 자동화에는 아주 잘 맞습니다. 반대로 은행·의료 같은 미션 크리티컬 시스템, 복잡한 비즈니스 로직, 보안이나 개인정보가 걸린 곳은 조심해야 합니다.

그렇다고 거기서 쓰지 말라는 게 아닙니다. 교육의 결론은 **핵심 구현과 검증 단계에서 Vibe Coding에만 의존하지 말라**는 거였습니다. 빠른 실험은 Vibe Coding으로 하고, 중요한 부분은 TDD와 코드 리뷰를 섞는 하이브리드가 현실적인 답입니다.

위험도 분명히 있습니다. AI가 보안 결함을 슬쩍 넣을 수 있고, 코드를 이해 못 한 채 쌓이면 나중에 유지보수가 어려워지고, 우리 디버깅 실력이 떨어질 수도 있습니다.
